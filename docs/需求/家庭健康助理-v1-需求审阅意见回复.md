# 家庭健康助理 v1 需求审阅意见回复

> 文档状态：审阅回复（待合并）  
> 日期：2026-09-07  
> 适用范围：针对《家庭健康助理-v1-需求审阅意见.md》的逐项回复与修订决策

## 1. 回复结论

感谢本次审阅。审阅意见准确指出了检索口径、网页读取、PIN 恢复、提醒降级、长文件处理、上下文成本和异机备份等需要澄清的事项。

经讨论，决定吸收其中的产品目标和风险控制要求，但不将固定技术实现、视觉样式或未经验证的数值上限直接写入产品需求。需求文档继续回答“产品必须达到什么效果”；检索算法、Token 分配、文件处理方式、备份加密算法等进入后续设计与配置。

同时形成以下新增原则：

- 除管理员外，普通家庭成员的使用应尽量接近正常聊天，不要求理解账号、档案、事件类型、插件或系统配置；
- 取消普通成员 PIN，使用一次性邀请链接或二维码、设备长期登录、管理员撤销与重新邀请；
- 不采用固定 4k～8k 的小型上下文窗口，v1 默认输入预算暂定 256k，并允许按模型能力和运行效果配置；
- 永久保存全部历史，但每轮只选择与当前问题相关的内容发送给模型；
- v1 不建设管理员 Web 后台，管理员通过配置、Secrets、管理 CLI、日志和只读查询运维；
- 管理操作不得依赖日常手写 SQL 绕过校验和审计；
- v1 按需接入营养、天气和地点 API，每日自动天气简报仍放入后续版本。

## 2. 对重点问题的逐项回复

### 2.1 关于“不做 RAG”与“相关性检索”

**回复结论：接受问题，部分接受建议。**

v1 不建设向量知识库、Embedding 流水线或通用 RAG 系统，但仍必须能够从长期记录中找出与当前问题相关的成员、时间和健康事件。二者并不冲突。

需求文档将补充：

> v1 必须按当前问题选择相关历史，不要求使用向量检索，也不得默认把全部家庭历史发送给模型。

审阅意见提出的“结构化元数据 + FTS + 固定滑动窗口”属于合理候选方案，但属于架构设计，不在产品需求中锁定。后续可以使用成员、时间、事件类别、关键词、摘要等方式组合检索。

### 2.2 关于多 LLM 的范围张力

**回复结论：接受。**

v1 明确只实现单模型处理，不实现多模型讨论、审查、投票或裁判。需求文档中的多 LLM 内容将收缩为未来扩展要求：

- 模型供应商可替换；
- 记录模型、耗时、Token、费用与错误；
- 健康业务与模型调用保持分离；
- 后续允许通过重构增加多模型协作；
- 如果提前预留会明显增加 v1 复杂度，不要求为多 LLM 预开发编排系统。

生成加审查、并行专家和候选加裁判等具体机制移入后续设计或路线图，不作为 v1 验收内容。

### 2.3 关于网页链接读取

**回复结论：部分接受，收窄范围。**

v1 支持用户发送公开网页链接，Agent 可以尝试提取公开正文，用于分析体检项目列表、地点和其他相关资料。

产品边界如下：

- 不保证支持登录页面、付费页面或依赖复杂交互才能显示的内容；
- 获取失败时提示用户复制文字、截图或上传 PDF；
- 禁止通过该能力访问服务器本机、内网地址和受保护基础设施；
- 不将网页内容视为天然可信事实，回答应结合来源和时效性；
- 超时和最大解析体积必须可配置。

审阅意见中的 5 秒和 200KB 不写死在需求文档中，待选定实现方式并实测后进入设计和配置。

### 2.4 关于药名、剂量、过敏等确认闭环

**回复结论：接受产品目标。**

v1 不建设药箱、疾病字典或独立用药管理模块。药名、剂量、频率、过敏和体检数值等关键数据依托聊天中的轻量记忆确认完成闭环：

- Agent 在聊天中展示识别结果；
- 用户可以点击确认、修改或不记录；
- 用户也可以直接通过文字或语音自然确认和纠正；
- 未确认的关键数据不作为正式健康事实使用。

具体卡片字段和持久化状态属于设计内容，不在需求中规定字段名称。

### 2.5 关于 Android PWA 推送降级

**回复结论：接受补强。**

现有需求已经要求应用内保留提醒状态，并明确 Web Push 不具备医疗级可靠性。在此基础上补充：

- PWA 聊天首屏应明显显示今日待办和逾期提醒；
- 用户当天再次打开应用或首次发起对话时，Agent 可以顺带提示由用户主动创建且已经到期或即将到期的提醒；
- 这种提示属于用户已创建提醒的补充送达，不视为未经请求的主动健康建议；
- 后续允许增加备用通知渠道，但 v1 不指定 Bark、微信或 Telegram 等具体产品。

### 2.6 关于 PIN 生命周期

**回复结论：不采用完善 PIN 生命周期的建议，改为删除 PIN。**

本项目只服务一个自有家庭，家庭管理员可以直接处理新设备和登录恢复。为降低老人和普通成员的使用负担，v1 不要求其设置或记忆 PIN。

身份流程调整为：

1. 管理员创建家庭成员；
2. 管理员生成一次性邀请链接或二维码；
3. 成员首次打开后设备长期登录；
4. 手机丢失时，管理员撤销旧设备；
5. 换机或登录失效时，管理员重新生成邀请链接或二维码。

管理员自身的系统访问需要可靠认证，具体方式在设计阶段确定。

### 2.7 关于录音和 PDF 上限

**回复结论：接受需要边界，不接受当前固定上限。**

医嘱录音可能自然达到 10～20 分钟，体检 PDF 也可能超过 30 页。直接把录音限制为 5 分钟可能破坏已确认的核心场景。

需求文档将要求：

- 音频、图片和 PDF 必须有可配置的大小、时长和页数上限；
- 超限时给出清晰提示；
- 条件允许时支持分段上传或后台分段处理；
- 长任务显示上传、转写、解析、比对和生成等阶段状态；
- 处理失败不能丢失已经上传的原始文件；
- 具体上限在确定 API 供应商并完成实测后写入设计与运行配置。

5 分钟、20MB 和 30 页可以作为测试候选，不作为现阶段正式需求基线。

### 2.8 关于记忆修改与撤回交互

**回复结论：核心要求已覆盖，接受结果反馈补充。**

普通成员使用应保持聊天无感。记忆处理采用双通道：

- Agent 在对话中用简短自然语言提示“已记住”；
- 必要时显示轻量的修改、撤回或确认操作；
- 用户可以直接说“别记了”“刚才说错了”“撤销上一条”；
- 修改或撤回完成后必须立即给出清晰结果反馈。

不要求用户进入独立记忆管理页面。Chip、颜色和删除线等具体视觉表达进入交互设计，不写入产品需求。

### 2.9 关于上下文与费用防御

**回复结论：接受需要管理上下文，不接受固定 4k～8k 和默认费用硬熔断。**

当前主流模型可以提供较长上下文。家庭正常聊天在早期不一定迅速达到上限，因此 v1 不为节省少量费用而过早压缩关键健康资料。

确定要求如下：

- 原始对话和附件永久保存；
- 每轮根据当前问题正常筛选需要发送的成员资料、近期事件和相关历史；
- v1 默认输入上下文预算暂定 256k，并做成管理员可配置项；
- 实际可用预算不得超过当前 Provider 声明的模型上下文能力，并应为模型输出和工具结果留出空间；
- 超过预算时优先分批处理、摘要旧内容或明确告知用户，不得静默遗漏关键依据；
- v1 记录调用量、Token 和费用，供管理员通过日志或 CLI 查看；
- v1 不设置自动停止普通家庭聊天的月度费用硬阈值，后续有实际费用数据后再决定是否增加告警或限制。

最近轮数、事件 Top-K、摘要方法和精确 Token 分配属于设计与配置。

### 2.10 关于异机加密备份

**回复结论：接受方向，不锁定供应商和算法。**

需求文档将明确至少支持一种由管理员提供的异机备份目标，例如：

- S3 兼容对象存储；
- NAS；
- WebDAV；
- 其他可验证的远程存储。

备份必须离开当前服务器、加密、保留历史版本并完成真实恢复演练。Cloudflare R2、阿里云 OSS 和具体加密算法属于部署设计选择，不写死在产品需求中。备份凭据不得进入代码库或普通日志。

## 3. 关于管理员后台的补充决策

**决定：v1 不建设管理员 Web 后台。**

本项目只服务一个自有家庭，管理员具备服务器运维能力。为减少无价值的页面、权限和表单工作，v1 采用：

- 版本化配置文件：普通运行参数和功能开关；
- Secrets：API 密钥和存储凭据；
- 管理 CLI：成员、邀请、设备、记忆、失败任务和备份操作；
- 结构化日志：错误、模型调用、Token 和费用；
- 必要的数据库只读查询：诊断和审计。

常规数据修改应通过带校验和审计的管理 CLI 完成，不建议日常手写 SQL 修改业务数据。

普通成员 PWA 不提供复杂管理页面，主要保留：

- 正常聊天；
- 文字、语音、图片、PDF 和链接输入；
- 回复朗读；
- 通知授权；
- 今日待办提示；
- 必要的记忆确认、修改和撤回；
- 当前身份、应用版本和退出设备等最小信息。

如果后续实际使用发现某项管理员操作频繁，再为该项建设 Web 页面。

## 4. 审阅意见之外发现的需求矛盾

### 4.1 天气能力范围

当前需求第 4 节仍将“天气与症状关联”列为 v1 非目标，但后文已经确认 v1 支持按需调用天气 API，并结合成员近期健康状态回答保暖、运动和出行问题。

修订时应改为：

- v1 支持用户提问时按需调用天气 API 并综合健康记录；
- v1 不做每日自动天气简报；
- v1 不做持续环境监控或未经用户请求的主动环境建议。

### 4.2 管理员 Web 后台范围

当前需求仍把最小管理员后台列为 v1 必须实现，与本次确认的 CLI 运维方案冲突。修订时应删除管理员 Web 后台要求，并用配置、Secrets、管理 CLI、日志和只读查询替代。

### 4.3 普通成员的无感使用原则

需求中已有适老化和聊天优先要求，但还应提升为全局产品原则：

> 除管理员外，家庭成员完成日常记录、查询、提醒和纠错时，应尽量只需自然聊天；除邀请登录和系统权限授权外，不要求其配置账号、维护档案或进入专门管理页面。

## 6. 后续处理

在本回复获得确认后，对《家庭健康助理-v1-产品需求.md》进行一次统一修订，而不是零散追加条款。修订内容包括：

1. 删除普通成员 PIN；
2. 增加普通成员无感聊天原则；
3. 删除 v1 管理员 Web 后台，替换为配置与管理 CLI；
4. 修正天气能力范围矛盾；
5. 明确 v1 相关历史选择与不建设向量 RAG；
6. 将上下文默认预算暂定为可配置的 256k；
7. 收缩多 LLM 章节；
8. 明确有限网页读取边界；
9. 补充关键数据聊天内确认、提醒降级和长文件处理要求；
10. 补充异机备份目标类别；
11. 删除已被新决定替代的管理员后台验收项和 PIN 验收项；
12. 检查全部 v1 功能清单、非目标、待确认事项和验收场景的一致性。
