## 3. 重点问题与改进建议（分类评析）

### 3.1 范围界定与概念一致性问题（Scope & Consistency）

#### 问题 1：非目标“不做 RAG”与多处“多维相关性检索”的工程落地定义不清晰
- **现状**：
  - 第 4 节（非目标）明确排除 `RAG 向量知识库`；
  - 但第 7.5 节、12.6 节、14.1 节多次强调：“面对用户问题时，系统需要能够按成员、时间范围、事件类别、家庭共同事件和当前问题相关性检索历史，再交给大模型综合分析”、“围绕当前问题检索相关信息，不应每轮把全家全部资料发送给模型”。
- **风险**：
  研发人员在实现时容易困惑：在没有向量知识库（RAG）的前提下，“当前问题相关性检索”与“跨维度检索”该如何实现？如果不予明确，可能滑向“全量数据暴力塞入 Context”或“偷跑轻量向量检索”。
- **建议**：
  在需求文档中对 v1 的“相关性检索”进行明确的降级定义：
  > **v1 检索机制**：基于**结构化元数据过滤**（成员 ID、时间窗口、事件类型 tags）结合**全文关键词匹配（FTS）**与**固定滑动窗口**提取候选上下文，再经由系统提示词编排送入大模型，**不引入向量化嵌入（Embedding）与向量检索数据库**。

#### 问题 2：多 LLM 协作在非目标与后文扩展中的表述张力
- **现状**：
  - 第 4 节非目标列出 `多 Agent 或多 LLM 协作`；
  - 第 22 节（多 LLM 扩展要求）与第 24.4 节却用了显著篇幅描述未来“生成加审查、并行专家、多方案加裁判”等机制。
- **建议**：
  虽然第 22 节后文加了“不属于硬性要求”的补充说明，但建议将第 22 节标题与重心调整为**“LLM Provider 抽象与调用度量要求”**，重点强调“单次调用记账（模型、耗时、Token、费用）与 Provider 解耦”，明确指出“多 LLM 编排机制（如审查、裁判）全量划入 v2 路线图，v1 仅实现单一 LLM 调用与失败重试”，避免团队在 v1 阶段过度设计复杂的编排层。

#### 问题 3：网页链接读取（Web Fetching）的产品边界不一致
- **现状**：
  - 第 9.1 节与第 23.1 节（条目 23）将“用户提供的体检项目清单或网页链接”列为 v1 必须支持；
  - 但第 27 节待确认事项中又提出：“是否需要在 v1 支持通用网页读取，以及允许访问的网络范围”。
- **风险**：
  通用网页抓取涉及动态渲染（SPA）、防爬反爬、内网穿透与 SSRF 安全风险，对于自建家庭服务是潜在的维护黑洞。
- **建议**：
  建议 v1 **收缩此功能范围**：
  1. 优先推荐用户直接复制网页文本或体检项目清单（纯文本或拍照/PDF）发送；
  2. 若保留 URL 读取，严格限制仅支持公网 HTTP/HTTPS 纯静态文本抓取（设定超时时间 5s、最大解析体积 200KB），严禁内网 IP 访问，明确不支持需要登录或复杂 JS 渲染的页面。

#### 问题 4：“无独立用药/过敏模块”与“高准确性数据确认”的操作闭环
- **现状**：
  - 第 4 节与第 23.2 节排除了“专门的药物相互作用规则引擎”和“独立用药、过敏和疾病管理模块”；
  - 但第 11.1、11.3、12.10 节要求：“体检数值、药名、剂量和过敏等高准确性数据确认后成为正式记忆”、“对关键药名、剂量、频率和时间要求用户确认”。
- **建议**：
  明确 v1 的产品承载载体：这类高敏感数据在 v1 依托**“带结构化属性的健康记忆卡片”**或**“医疗事件流水记录”**实现，系统仅通过对话生成【待确认卡片】，用户在界面点击【确认】或自然语言确认后打上 `confirmed: true` 标记即可，无需跳转或维护专用的药箱/疾病字典数据库。

### 3.2 用户体验与适老化细节审查（UX & Accessibility）

#### 问题 5：Android PWA Web Push 可靠性不足的降级交互缺失
- **现状**：
  - 第 15.3 节提出“主要通过 Android PWA 系统通知弹出”，并指出“受系统权限和后台限制影响，不宣称具备医疗级报警可靠性”。
  - 国内安卓主流 ROM（MIUI、ColorOS、OriginOS、HarmonyOS）普遍不具备原生 Google Play Services 环境，PWA Service Worker 易被系统后台查杀，纯依赖 Web Push 会导致提醒漏发率较高。
- **建议**：
  增加**应用内高可见度提醒兜底机制**：
  1. **首屏常驻待办入口**：PWA 聊天首屏顶部展示“今日提醒”常驻胶囊标签，红点提示待执行事项；
  2. **会话首轮被动唤起**：当成员当天首次与助理对话时，若存在已到期或即将到期的提醒，助理在第一句回复末尾自然附带轻量提示（如：“顺便提醒您，今天的降压药还没标记服用哦”）；
  3. **长线规划备用渠道**：在第 24 节（扩展路线）补充通过 Bark / 微信测试号 / Telegram Bot 等高可达渠道推送的可行性预留。

#### 问题 6：PIN 码生命周期与老人遗忘恢复机制
- **现状**：
  - 第 8.1 节说明“使用简单 PIN 作为换设备或登录失效时的兜底”，但未定义 PIN 码的初始化与重置机制。
  - 老年人群体极易遗忘数字 PIN。
- **建议**：
  1. **初始化**：支持管理员在后台直接为老人预设初始 PIN，或在生成邀请链接时由管理员配置；
  2. **找回与重置**：不设计复杂的自助密保，明确规定“若成员遗忘 PIN，直接联系家庭管理员，由管理员后台一键重置 PIN 或重新生成一次性激活二维码/链接”；
  3. **失效注销**：管理员在后台撤销某设备时，服务端立即失效关联 Token，设备下次请求时强制跳转 PIN/邀请码验证。

#### 问题 7：就医录音与体检 PDF 的工程与体验规格上限
- **现状**：
  - 第 12.10 节（医嘱录音理解）与第 9.3 节（多页 PDF）未给出文件规格与输入上限约束。
  - 就医现场录音容易长达 10~20 分钟；全身体检报告 PDF 常常多达 30~50 页。
- **建议**：
  在产品需求层明确给出体验与性能的规格边界：
  - **单段音频录音**：上限建议设为 **5 分钟**（提示用户分段录制重点医嘱，避免 ASR 超时与高昂计费）；
  - **体检报告 PDF**：单文件建议上限 **20MB / 30 页**。若超过页数，提示用户分拆或优先上传带有“汇总/异常项说明”的关键页；
  - **处理中感知**：大文件处理期间，在消息流中呈现清晰的阶段状态机提示（如“正在上传 45% -> 正在提取文字 -> 正在比对往年指标 -> 马上就好”），避免老人误以为卡死。

#### 问题 8：记忆提示与撤回的“双模”交互平衡
- **现状**：
  - 第 11.2 节要求提取记忆后向用户显示轻量提示（如“已记住：晚餐半碗米饭”），并支持修改和撤回。
- **建议**：
  明确前端展示形态采用**“微卡片 + 操作 Chip”**设计：
  - 每条生成记忆的气泡右下角附带极简的 `[修改]`、`[撤回]` 文字小按钮（便于年轻人轻点即改）；
  - 同时后端核心意图识别支持对上一轮记忆的自然语言指令（如“别记了”、“撤销”）（便于老人直接通过语音/文字撤销）；
  - 撤回后，前端卡片状态瞬时变为浅灰色划线样式“已撤回”，给用户明确的正向安全反馈。

### 3.3 非功能性与数据安全审查（Non-Functional & Security）

#### 问题 9：Token 上下文装配策略与费用防御
- **现状**：
  - 需求中多次描述了强大的综合分析场景（睡眠 + 体重 + 早餐 + 往期疾病 + 家庭公共信息 + 天气），如果检索逻辑缺乏约束，会导致单次对话拼入数万 Token。
- **建议**：
  在第 14 节或第 20 节补充**“上下文装配节流规则”**：
  - 严格限制送入大模型的单次对话上下文深度（如最近 5~10 轮）；
  - 检索的历史事件按“近期核心事实（近 7 天）+ 关键健康档案摘要（如过敏原、基础病）+ 当前问题相关度 Top-K”进行摘要压缩与硬截断，控制单次 Prompt 规模在合理区间（如 4k~8k tokens 内），防止月度 API 账单超支。

#### 问题 10：异机加密备份的介质要求落地
- **现状**：
  - 第 17.3 节要求“自动备份，不能只保存在同一磁盘，加密，保留多个历史版本，恢复演练”。
- **建议**：
  由于本项目部署在自有单机服务器（`ssh jd`），“异机”必须有明确的物理落地指引。建议补充说明：
  > 备份脚本支持导出本地加密归档包（如 AES-256），并通过标准协议定期同步至外部存储，如**用户提供的 S3 兼容对象存储（Cloudflare R2 / 阿里云 OSS 等）**或**家庭私有 NAS / WebDAV**。

## 5. 结论与后续推进建议

### 5.1 结论
《家庭健康助理-v1-产品需求.md》是一份思考极其深入、业务边界高度克制、场景贴合现实的优秀需求文档。它在“保护家庭健康隐私”与“借助前沿大模型能力”之间取得了极佳的平衡。

在吸收本审阅意见中的微调建议（主要是明确检索机制、补充通知降级、限定输入规格、细化 PIN 码运维闭环）后，即可**作为 v1 的正式需求基线定稿**。
