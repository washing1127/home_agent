# 家庭健康助理 v1 需求变更申请回复

> 文档状态：批准并已合入需求基线  
> 日期：2026-09-07  
> 适用范围：针对《家庭健康助理-v1-需求变更申请.md》的正式回复

## 1. 回复结论

本次申请提出的两项产品目标均予以采纳，并已按需求层级重新表述后合入《家庭健康助理-v1-产品需求.md》：

1. 将“处理期间继续发送消息、旧回复失效和后续重新综合”纳入 v1；
2. 将“记录者、多名相关成员、共同事件和个人明细”纳入 v1；
3. 不在需求文档中锁定 Agent Run、数据表、状态枚举或进度摘要的具体实现；
4. 不采用含义宽泛的通用“影响范围”字段，改用相关成员，并仅在计划、建议、提醒或家庭规则确有需要时表达适用成员；
5. 增加相应异常处理、审计要求、v1 功能项和验收场景。

## 2. 关于连续消息与旧回复失效

### 2.1 批准的产品行为

- Agent 正在处理时，用户仍可继续发送消息，新消息必须先保存；
- 新消息到达后，尚未完成且基于旧上下文的回复失效，不得继续启动新工具或执行尚未开始的动作；
- 后续处理重新综合新消息、已有对话、可安全复用的处理结果和已经生效的业务变更；
- 已开始且安全、可复用的转写或附件解析任务不必随旧回复一并取消；
- 未执行、未校验或待确认的动作不得视为已经生效；
- 结果未知的外部写操作必须先核对，不得直接重复；
- 被取代的处理过程、未完成回复和相关调用记录必须可审计。

### 2.2 对已提交业务变更的补充

“不因技术性中断自动回滚”不表示忽略用户纠错。已经成功提交的结果原则上保留，但用户明确纠正或否定旧结果时，系统必须修改、撤回或建立更正记录，并保留来源和审计关系。

例如，旧处理已经将“体温 38.5℃”记录到爸爸名下，随后用户补充“刚才说的是乐乐”，系统不得继续保留该记录为爸爸的有效事实，应按既有记忆修正或撤回规则完成纠正。

### 2.3 留待设计决定的内容

以下属于总体设计，不写入产品需求的具体实现约束：

- 是否每条消息对应一个 Agent Run；
- Run 的状态枚举和取代关系；
- 连续消息的合并窗口；
- 结构化进度摘要的格式；
- 模型流式输出的终止机制；
- 后台任务取消和结果复用的技术方案。

## 3. 关于记录者、相关成员与共同事件

### 3.1 批准的产品行为

- 结构化健康记录必须保存记录者、相关成员、来源和确认状态；
- 记录者由服务端可信身份确定，模型不得提供或覆盖；
- 一条共同事件可以关联多名成员；
- 相关成员不明确且影响归属时必须追问；
- 每名成员不同的发生时间、程度、摄入量等信息保存为个人明细，并关联共同事件；
- 计划、建议、提醒或家庭规则确有需要时，可以另行表达适用成员。

### 3.2 明确区分的概念

系统不得混淆以下概念：

- 记录者：实际提交信息的人；
- 相关成员：事件实际涉及的人；
- 适用成员：计划、建议、提醒或规则适用于谁；
- 数据访问权限：谁可以查询数据；
- 家庭公共知识：家庭明确要求长期共享记住的内容。

普通成员可以查询其他成员，不会使个人事件自动成为共同事件；共同事件关联多人，也不会自动写入家庭公共知识。

## 5. 对总体设计的要求

总体设计需要给出一种满足上述产品行为的实现方案，至少覆盖：

- 同一对话中处理过程的串行化、取代或合并策略；
- 旧回复失效与流式输出终止；
- 模型决策、基础处理任务和业务动作之间的边界；
- 工具调用及外部写操作的幂等与结果核对；
- 已提交结果的纠正、撤回和审计关系；
- 多成员共同事件、个人明细及相关检索方式。

设计应优先采用可理解、可测试的简单方案，不为后续假设场景提前引入分布式工作流或复杂事件编排平台。
