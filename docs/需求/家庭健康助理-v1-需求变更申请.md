# 家庭健康助理 v1 需求变更申请

> 文档状态：变更申请（修订版，已批准）  
> 日期：2026-09-07  
> 适用范围：家庭健康助理 v1 运行中消息处理与健康信息归属  
> 关联需求：`家庭健康助理-v1-产品需求.md`  
> 说明：本文仅提出需求修改建议，不直接修改需求基线；是否采纳及如何写入基线由需求方决定。

## 1. 申请背景

总体设计讨论中确认，用户在 Agent 正在理解消息、调用工具或生成回复时，仍应能够继续发送补充、纠正或取消消息。新消息到达后，系统不能继续盲目执行已经过时的处理计划，也不能丢弃旧运行已经安全保存的内容和已经完成的有效结果。

讨论同时进一步明确：为了支持按成员检索、代家人记录和跨成员分析，业务记录除实际操作者和事件主体外，还需要明确表达该记录影响或适用的成员范围，并支持一条共同事件关联多名成员。

现有需求已经规定原始数据先保存、长任务状态可见、任务可重试、操作者与事件主体分离，以及家庭共同事件等原则，但尚未完整规定上述两项行为，故提交本申请。

## 2. 建议变更一：支持运行中补充消息与旧回复失效

### 2.1 建议级别

新增产品行为。

### 2.2 建议需求

1. Agent 正在处理当前对话时，用户仍可继续发送文字、语音、图片、PDF 或其他受支持的消息，新消息必须立即保存。
2. 同一对话在生成回复期间收到新消息时，尚未完成的旧回复应失效。系统不得继续依据已经过时的上下文作出新的模型决策、启动新的工具调用或执行尚未开始的业务动作。
3. 后续回答必须重新综合尚未处理的新消息、已有对话、可以安全复用的处理结果，以及已经成功提交且仍然有效的业务变更。
4. 语音转写、图片或 PDF 解析等已经开始且安全、可复用的基础处理任务，可以继续执行；用户明确要求取消处理时，系统应尽力取消尚可取消的任务。
5. 已经成功提交的业务变更不因技术性中断而直接删除；但新消息明确纠正或否定旧结果时，系统必须修改、撤回或建立更正记录，并保留完整的来源与审计关系。
6. 已提出但尚未执行、尚未通过校验或仍在等待确认的业务动作，不得因旧回复曾经建议过而被视为已经生效。
7. 已经发出但结果未知的外部写操作，应先查询或核对执行结果，不得直接重复执行。
8. 被新消息取代的处理过程仍应可审计，不得删除其消息、附件、处理状态、模型调用、工具调用、错误或动作记录；不要求保存或传递模型的原始内部推理过程。
9. PWA 应明确显示旧回复已停止、正在结合新消息重新处理，或基础附件任务仍在继续等必要状态；已经展示的未完成回复不得伪装成完整有效回复。

### 2.3 建议验收场景

1. 用户发送“记录我今天体温 38.5℃”，在 Agent 回复前补充“刚才说的是乐乐，不是我”；系统使旧回复失效，以乐乐为主体重新处理，并保留两条原始消息和处理记录。
2. 用户上传体检 PDF，在解析过程中补充报告所属成员；已经完成的页面解析结果得到复用，新运行按正确成员继续处理。
3. 旧处理在失效前已经成功创建一条普通健康事件；后续处理不得重复创建，也不得假装该事件没有发生；如果新消息明确纠正该事件，系统应修改、撤回或建立更正记录。
4. 旧运行仅提出一条提醒候选但尚未得到用户确认；被新消息中断后，该提醒不得自动创建。
5. 用户明确说“不要继续处理刚才的文件”；系统保留已上传原件，并取消或停止后续仍可取消的处理步骤。

## 3. 建议变更二：明确记录者、相关成员与共同事件

### 3.1 建议级别

对现有操作者与事件主体规则、家庭共同事件规则的补充澄清。

### 3.2 建议需求

1. 每条结构化健康记录均应明确保存记录者、相关成员、来源和确认状态，不得只将这些信息保留在自然语言正文中。
2. 记录者由服务端可信会话及后续确认操作确定，模型不得提供或覆盖实际登录操作者。
3. 一条记录可以关联一名或多名成员；相关成员不明确且会影响数据归属时，系统必须追问。
4. 用户明确表示某事件为家庭共同经历时，系统可以建立一条共同事件并关联相关成员。
5. 共同事件中各成员存在不同时间、程度、摄入量或其他个体差异时，应另行保存个人明细事件，并保留其与共同事件的关联。
6. 对计划、建议、提醒或家庭规则等确有需要的内容，可以另行表达其适用成员；适用成员不等同于记录者、事件相关成员、数据访问权限或家庭公共知识。
7. 家庭公共知识仍仅在用户明确表达家庭共享和记忆意图时写入。共同事件关联多名成员，不等于自动形成家庭公共知识。

### 3.3 建议验收场景

1. 爸爸记录“乐乐体温 38.5℃”；记录者为爸爸，相关成员为乐乐。
2. 妈妈记录“我们三个人今天都腹泻了”；系统确认具体成员后建立关联三人的共同事件，并允许分别补充每人的开始时间和严重程度。
3. 爸爸说“全家记住，这周都低盐饮食”；系统记录该计划适用于全家，并按现有规则写入家庭公共知识。
4. 普通成员能够查询其他成员不代表个人事件自动变成共同事件，系统不得混淆数据访问权限、相关成员、适用成员与家庭公共知识。

## 4. 对既有需求的影响

建议需求方评审时重点检查以下既有章节是否需要补充：

- 第 7.4 节“通用健康事件流水”；
- 第 9 节“多模态聊天”；
- 第 10 节“对话行为”；
- 第 11.3 节“记忆状态”；
- 第 11.4 节“代家人记录”；
- 第 14 节“家庭成员查询与公共知识”；
- 第 18 节“异常与降级体验”；
- 第 20 节“AI 可审计性”；
- 第 25 节“验收场景”。

本申请不改变以下既有要求：

- 原始消息和附件永久保存；
- 身份、权限、数据写入和确认由服务端业务逻辑保证；
- 普通成员可以代其他成员记录并查询其他成员信息；
- 关键健康事实确认后才成为正式事实；
- v1 家庭公共知识仅在用户明确要求时写入；
- 外部 API 失败和任务重试不得导致消息丢失或重复写入。

## 5. 对总体设计的影响

若需求方采纳，本次变更需要总体设计支持：

- 能够独立追踪消息处理过程及其完成、失败、取消或被取代状态；
- 被取代的处理过程与后续处理之间保留可审计关系和可验证结果交接；
- 工具结果、动作建议与实际执行结果分开保存；
- 后台基础处理任务与 Agent 决策过程可以分别取消和复用；
- 健康事件支持多成员关联、共同事件与个人明细事件；
- 检索可以分别按记录者、相关成员和适用成员筛选。

具体状态、数据表、接口和后台任务实现属于总体设计与后续详细设计，不在本申请中规定。

## 6. 请求需求方决定

请需求方分别决定：

1. 是否将“运行中补充消息与可中断 Agent 运行”纳入 v1 产品需求基线；
2. 是否将“记录者、相关成员、共同事件与个人明细”作为现有数据归属规则的正式澄清；
3. 是否需要增加或调整相关验收场景；
4. 经批准后，由需求方修改 `家庭健康助理-v1-产品需求.md` 并更新其文档状态或版本记录。
