# 家庭健康助理 v1 产品需求文档

> 文档状态：需求基线（定稿版）  
> 日期：2026-09-07  
> 适用范围：仅服务一个自有家庭的首个可用版本

## 1. 文档目的

本文档定义家庭健康助理 v1 的产品目标、用户、核心概念、功能范围、行为规则、数据要求、非功能要求和验收标准。本文档回答“产品要做什么”，不规定数据库表、服务拆分、框架选型等详细实现方式。

## 2. 产品定位

家庭健康助理是部署在自有远程服务器上的家庭 AI 助理。每位家庭成员可通过手机 PWA 独立与其交流，系统长期保存家庭健康资料和对话，并基于个人历史与家庭信息提供连续、个性化的健康支持。

产品首先聚焦健康领域，但定位是健康助理而不是医生：可以解释、整理、比较和提供一般性建议，不声称作出医学诊断，也不替代医生、急救服务或专业医疗决策。

本产品与普通健康 App 的核心区别是：

- 数据由家庭自己掌握；
- 不只围绕单个用户，而是围绕家庭共同生活形成长期记忆；
- 每人独立交流，同时允许家人相互查询和代为记录；
- 饮食、疾病、体检、照护等事件能够跨时间积累和关联；
- 所有重要记忆均可追溯到原始对话或附件。

### 2.1 普通成员无感使用原则

除管理员外，家庭成员完成日常记录、查询、提醒和纠错时，应尽量只需像使用普通聊天软件一样自然交流。除首次邀请登录、麦克风和通知等系统权限授权外，不要求普通成员配置账号、维护档案、理解事件类别或进入专门管理页面。

系统内部可以进行结构化记录、检索和工具调用，但不应把这些复杂性转嫁给普通成员。必要的确认、修改和撤回应在对话中通过简短提示、轻量操作或自然语言完成。

## 3. v1 产品目标

v1 的目标不是建设完整的健康管理平台，而是验证以下核心价值：

1. 家庭成员是否愿意自然地通过聊天长期使用助理；
2. 助理是否能正确区分操作者与健康事件主体；
3. 助理是否能从聊天、语音、图片和 PDF 中形成可靠的长期健康记忆；
4. 家人询问彼此健康状况时，助理能否基于实际记录给出有用总结；
5. 助理能否支持饮食记录、体检历史理解和个性化体检建议三个重点场景；
6. 用户主动创建的提醒能否可靠送达。

## 4. 非目标

v1 不以商业化、多家庭服务、医疗诊断或医疗级监护为目标，也不追求完整覆盖所有健康管理功能。

以下内容不属于 v1：

- 多家庭注册、租户管理、计费和套餐；
- 原生 Android/iOS App；
- IM 机器人；
- 实时语音通话；
- 家庭药箱、库存和有效期管理；
- 专门的药物相互作用规则引擎；
- 主动健康采访；
- 沉默检测；
- 提醒逾期后自动通知其他家人；
- 就诊前一页纸和医嘱任务化；
- 家族病史树；
- 复杂健康趋势仪表盘；
- 管理员 Web 后台；
- 开放式第三方插件安装；
- 多 Agent 或多 LLM 协作编排；
- 本地模型部署；
- 向量知识库、Embedding 流水线和通用 RAG 系统；
- 每日自动天气简报；
- 持续环境监控和未经用户触发的环境健康建议。

## 5. 用户与角色

### 5.1 管理员

管理员负责家庭系统管理，并拥有全部数据的运维查看能力。v1 只有一个管理员，且管理员具备直接操作服务器的能力。

管理员可以：

- 创建家庭成员；
- 为可登录成员生成一次性邀请链接；
- 撤销设备登录状态；
- 查看全部成员的对话、附件、健康记忆、家庭公共知识和提醒；
- 修改或撤回错误记忆；
- 查看记忆的原始来源；
- 查看外部 API 错误、调用量和估算费用；
- 查看系统基本运行状态。

v1 不为上述能力建设 Web 后台。管理员通过版本化配置、Secrets、管理 CLI、结构化日志和必要的数据库只读查询完成运维。常规数据修改应通过带校验和审计的管理命令完成，不应依赖日常手写 SQL 绕过业务规则。

### 5.2 可登录成员

拥有独立身份、独立聊天空间和个人健康档案，可通过自己的设备使用助理。

### 5.3 受管理成员

没有手机或暂时不独立使用系统的家庭成员，例如儿童。受管理成员拥有独立健康档案和长期记忆，但没有登录凭证，其他家庭成员可以替其记录或查询。以后可以在不迁移数据的情况下开通登录能力。

### 5.4 操作者与事件主体

系统必须始终区分：

- 操作者：实际登录并发送消息的人；
- 事件主体：健康信息所描述的一名或多名相关成员。

例如爸爸登录后说“乐乐今天体温 38.5℃”，事件主体是乐乐，记录者是爸爸；如果他说“我们三个人今天都腹泻了”，同一共同事件可以关联三名成员。记录者和相关成员必须被结构化保存并可追溯。

## 6. 家庭信息原则

本产品以“家庭是共同体，健康事项可以由家庭共同了解和照护”为默认前提。

确定规则如下：

- 每位成员拥有独立账号、对话和按成员组织的健康档案；
- 管理员可以通过系统运维能力查看全部内容；
- 家庭成员可以询问其他家庭成员的健康状况；
- 助理可读取被询问成员的有效健康记忆并生成总结；
- 原始聊天不需要作为普通成员浏览他人的入口，跨成员查询由助理总结回答；
- v1 的家庭公共知识只有在成员明确要求时写入；
- 自动提取可能影响其他成员的信息并加入家庭公共知识的能力需要保留扩展位置，但 v1 默认关闭；
- 未经确认的 AI 推测不得作为事实写入正式健康记录。

## 7. 信息结构

系统概念上维护三类长期信息。

### 7.1 公共健康知识

营养学知识、健康指南、药品说明等外部知识。v1 主要依赖模型已有能力和当前问题所需的外部 API，不建设大型本地 RAG 知识库。

### 7.2 家庭公共知识

全家共同适用或明确要求家庭记住的信息，例如共同饮食安排、家庭近期传染风险或家庭物品位置。

v1 写入方式：

- 用户明确说“记录到家庭”“全家都记住”等指令后写入；
- 管理员可以查看、修改和撤回；
- 自动提取接口保留，但默认关闭。

### 7.3 个人健康档案与记忆

按成员独立组织，至少包括：

- 基础资料；
- 通用健康记忆；
- 饮食事件；
- 体检报告及指标；
- 与本人相关的提醒；
- 事件来源和修改历史。

家庭成员可通过助理查询其他成员的相关内容。

### 7.4 通用健康事件流水

v1 需要支持通过自然语言、语音和附件形成带时间的通用健康事件。事件可以包含少量结构化字段，但不要求每种事件建设独立业务模块或专门页面。

应支持的事件类别至少包括：

- 睡眠：入睡时间、起床时间、时长、主观质量；
- 身体测量：身高、体重、体温、血压及其他用户报告的数值；
- 饮食：食物、份量、餐次、估算营养和实际摄入；
- 运动：项目或动作、重量、组数、次数、时长及主观感受；
- 症状与疾病：表现、开始时间、持续时间、严重程度及变化；
- 日常健康：食欲、排便、精神状态、活动等；
- 医疗：体检、就诊、医嘱、复诊要求和相关附件；
- 计划：准备食用的餐食、家庭出行或其他需要健康辅助决策的计划。

所有事件均应保留记录者、一名或多名相关成员、发生时间、来源和确认状态。只涉及一名成员时，该成员即为事件主体；家庭共同经历可以形成关联多名成员的共同事件。事件类别用于检索与组织上下文，不限制大模型综合分析不同类别信息。

共同事件中各成员存在不同时间、程度、摄入量或其他个体差异时，应保存相应个人明细，并保留其与共同事件的关联。计划、建议、提醒或家庭规则确有需要时，可以另行标明适用成员；相关成员和适用成员均不代表数据访问权限，也不自动形成家庭公共知识。

### 7.5 多维检索与分析

面对用户问题时，系统需要能够按成员、时间范围、事件类别、家庭共同事件和当前问题相关性检索历史，再交给大模型综合分析。

v1 不要求使用向量检索。系统必须根据当前问题选择相关历史，不得默认把全部家庭历史直接发送给模型。具体的关键词、时间窗口、摘要或其他候选选择方式在设计阶段确定。

系统应支持：

- 同一成员跨时间分析，例如睡眠、体重、训练和饮食变化；
- 同一时间跨类型分析，例如头疼与近期睡眠不足的可能关联；
- 同类指标趋势分析，例如儿童身高体重、训练重量和体检指标；
- 跨成员同期事件分析，例如多名成员先后出现腹泻；
- 个人事件与家庭共同事件关联，例如共同饮食后多人不适；
- 个人健康资料与实时天气、地点或营养数据的综合判断。

分析和建议原则上由大模型完成，v1 不为睡眠、训练、症状或出行分别建设专用推理引擎。系统主要负责保存、检索、组织和提供可靠数据。

## 8. 首次建档与身份识别

### 8.1 创建与邀请

- 管理员预先创建家庭成员；
- 可登录成员通过一次性邀请链接或二维码首次进入；
- 首次使用后设备保持长期登录；
- 管理员可撤销具体设备的登录状态；
- 手机丢失时由管理员撤销旧设备；
- 换机或登录失效时由管理员重新生成一次性邀请链接或二维码；
- 客户端不能通过自行提交成员名称冒充另一成员，实际操作者由服务端可信身份确定。

### 8.2 极简首次建档

首次使用通过简短对话确认：

- 姓名；
- 助理使用的称呼；
- 出生年月；
- 性别；
- 身高。

体重、病史、过敏、用药、体检记录等在后续聊天和附件处理中逐步补全，不要求首次填写长表单。

## 9. 多模态聊天

### 9.1 支持的输入

v1 必须支持：

- 文字；
- 语音消息；
- 手机拍照；
- 相册图片；
- PDF 文件；
- 用户提供的网页链接或项目清单。

语音采用“录制后发送”，不做实时通话。ASR 需要能够支持家庭常用方言，具体能力由可替换的云 API 提供。

### 9.2 输出

- 助理默认返回文字；
- 每条助理回复提供“播放”按钮，通过 TTS 朗读同一文本；
- v1 不默认自动播放；
- 文字与语音内容保持一致，便于回看和审计。

### 9.3 附件理解

助理需要能够在聊天中：

- 识别并分析饭菜图片；
- 阅读体检报告、化验单和检查单；
- 理解药盒或处方图片；
- 阅读多页 PDF；
- 读取用户提供的体检项目、地点或其他相关网页链接；
- 在图片模糊、页面缺失或内容无法辨认时明确要求重拍或补充，而不是猜测。

网页链接仅支持用户主动提供的公开 HTTP/HTTPS 页面正文读取。系统不保证支持登录页面、付费页面或依赖复杂交互才能展示的内容；获取失败时应提示用户复制正文、发送截图或上传 PDF。网页读取不得访问服务器本机、内网地址或受保护基础设施，且不得把网页内容默认视为可信事实。

音频、图片和 PDF 必须具有可配置的大小、时长和页数上限。超限时应清晰提示；条件允许时支持分段上传或后台分段处理。长任务应展示上传、转写、解析、比对和生成等阶段状态。处理失败不得丢失已经上传成功的原始文件。具体限制在供应商确定并实测后配置。

ASR、TTS、图片和 PDF 理解均可由外部 API 完成，服务器不运行本地模型。v1 对首次输出时间不敏感，优先保证处理结果、错误可见性和数据不丢失。

## 10. 对话行为

### 10.1 个性化表达

助理根据不同成员调整：

- 称呼；
- 回答长短；
- 用词难度；
- 口语程度；
- 健康解释详细程度。

老人使用时应优先简短、直白、易听懂。初始偏好可由管理员设置，后续可根据交互逐步调整。

### 10.2 健康回答

- v1 不额外建立复杂医疗规则引擎，主要依赖所选大模型的既有安全对齐能力正常交流；
- 助理保持“健康助理而非医生”的身份；
- 可以解释报告、分析饮食、比较历史和推荐体检项目；
- 不确定时应明确表达不确定；
- 对明显紧急情况建议立即寻求真人、急救或专业医疗帮助；
- 不必在每条普通回复中机械重复免责声明；
- 不得把 AI 推测表述为已经确认的事实。

### 10.3 主动行为

v1 不主动采访、不因沉默而联系成员，也不主动发送未经用户请求的健康建议。只有用户明确创建的提醒可以主动推送。

### 10.4 相关性与因果表达

大模型可以基于历史记录提出可能关联和调整建议，但必须区分：

- 已确认事实；
- 历史数据中观察到的模式；
- 可能的解释；
- 需要进一步测量、观察或就医确认的判断。

缺少充分数据时，不应把相关性表述为确定因果，也不应给出无法从可靠数据支持的精确预测值。

### 10.5 连续消息与旧回复失效

- Agent 正在处理当前对话时，用户仍可继续发送任何受支持的消息，新消息必须立即保存；
- 同一对话在生成回复期间收到新消息时，尚未完成的旧回复应失效，系统不得继续依据过时上下文作出新的模型决策、启动新的工具调用或执行尚未开始的业务动作；
- 后续回答必须重新综合新消息、已有对话、可安全复用的处理结果，以及已经成功提交且仍然有效的业务变更；
- 已经开始且安全、可复用的语音转写、图片或 PDF 解析等基础任务可以继续；用户明确要求取消时，系统应尽力停止尚可取消的任务；
- 已提出但尚未执行、尚未通过校验或仍在等待确认的动作，不得被视为已经生效；结果未知的外部写操作必须先核对结果，不得直接重复；
- 被取代的处理过程及已经展示的未完成回复必须明确标记并保留审计记录，不得伪装成完整有效的回复；
- 系统只需继承可验证的进度和结果，不要求保存或传递模型的原始内部推理过程。

## 11. 长期记忆

### 11.1 记忆类型

v1 至少支持：

1. 成员基础档案；
2. 通用健康记忆；
3. 通用健康事件流水；
4. 体检报告及指标；
5. 用户提醒；
6. 家庭公共知识。

用药、过敏、病史等在 v1 可以先以通用健康记忆保存，不要求立即建设完整独立管理模块；但药名、剂量和过敏等关键内容必须准确标记并支持确认。

### 11.2 用户感知

系统提取记忆后应向用户显示轻量提示，例如：

> 已记住：2026 年 9 月 7 日晚餐，约半碗米饭和一份青菜。

提示应提供修改和撤回入口，或允许用户通过自然语言操作：

- “不要记这个”；
- “忘掉刚才那顿饭”；
- “刚才说错了”；
- “把体重改成 70 公斤”。

完成确认、修改或撤回后，系统必须立即在对话中给出明确反馈，不要求用户进入独立记忆管理页面。

### 11.3 记忆状态

- 普通饮食和一般健康事实可以自动记住并提示；
- 体检数值、药名、剂量和过敏等高准确性数据确认后成为正式记忆；
- 对主体、日期、数值或内容不确定时，系统先追问；
- 撤回后该记忆不得继续用于回答；
- 原始对话仍永久保存，并保留记忆曾被撤回的记录，避免以后重新提取为有效事实；
- 新旧记录冲突时，不应静默覆盖；应保留时间变化、询问用户，或由管理员纠正；
- 已成功提交的业务变更不因技术性中断而直接删除；新消息明确纠正或否定旧结果时，系统必须修改、撤回或建立更正记录；
- 每条记忆必须可以追溯到原始消息或附件。

关键数据通过对话内轻量提示完成确认。用户可以点击确认、修改或不记录，也可以直接通过文字或语音确认和纠正；v1 不为此建设独立药箱、疾病字典或用药管理页面。

### 11.4 代家人记录与共同事件

- 成员可以替其他成员记录健康信息，也可以记录多名成员共同经历的事件；
- 系统必须结构化保存记录者、相关成员和来源，实际记录者由服务端可信身份确定，模型不得覆盖；
- 相关成员不明确且会影响数据归属时必须追问；
- 体检报告、用药、过敏和关键指标等内容需要明确确认属于哪位成员；
- 共同事件中每名成员的时间、程度或其他细节不同时，应分别保存个人明细并关联共同事件；
- “我觉得妈妈最近状态不好”等观察应标明是记录人的描述，不得变成妈妈本人确认的事实。

## 12. 核心使用场景

### 12.1 饮食拍照与长期建议

用户拍摄一顿饭，可以同时使用文字或语音说明实际摄入量，例如“这碗米饭只吃了一半”。

系统需要：

- 默认将照片视为发送者自己的饮食；
- 结合图片和补充描述估算实际摄入，而非默认全部吃完；
- 识别主要食物、粗略份量和营养构成；
- 明确图片估算存在误差；
- 记录用餐日期、餐次、主要食物和实际摄入描述；
- 支持事后修正日期、餐次、食物归属和摄入量；
- 结合近期饮食和已有健康信息提供后续饮食建议；
- 支持回答长期问题，例如“最近蔬菜够不够”“这周是不是吃得太油”。

若用户明确说这是一顿家庭共同饮食，系统可以继续询问各成员的实际摄入；未说明时只记录到发送者名下。

### 12.2 查询其他成员健康状况

家庭成员可以问：

- “最近妈妈健康怎么样？”；
- “妈妈最近血压高吗？”；
- “小朋友上次体检有什么异常？”；
- “结合妈妈的情况，今晚做什么饭比较合适？”。

助理需要综合被询问成员的相关档案、健康记忆、饮食事件、体检数据和家庭公共知识，给出摘要，并明确：

- 数据覆盖的时间范围；
- 数据最后更新时间；
- 关键事实来源类型；
- 哪些信息不足或尚未确认。

没有记录不代表没有问题。系统不得把“没有相关数据”回答为“健康正常”。

### 12.3 体检报告理解与项目建议

用户可以上传图片或 PDF 体检报告。系统需要：

- 识别报告日期、机构、项目、结果、单位、参考范围和异常标记；
- 保留原始报告；
- 展示关键识别结果供用户确认或修正；
- 对无法辨认的字段标记为待确认，不得猜测；
- 解释异常指标；
- 比较不同日期的同类指标；
- 根据年龄、性别、历史报告、距上次检查时间、历史异常和已有风险因素，推荐本次体检项目；
- 对每个推荐项目说明原因；
- 指出哪些情况适合先咨询医生。

v1 不要求复杂体检管理页面或漂亮趋势图，但底层记录必须支持跨时间查询和比较。

### 12.4 睡眠、体重与综合健康建议

用户可以在一次对话中同时报告睡眠、起床时间、体重和早餐照片。助理需要：

- 分别记录相应健康事件；
- 根据饮食识别结果和营养数据估算蛋白质、碳水化合物、脂肪及热量；
- 对比近期体重、睡眠和饮食变化；
- 说明观察到的模式和不确定性；
- 给出可执行的饮食、作息和运动建议。

### 12.5 运动训练记录与分析

用户可以通过自然语言或语音记录当天训练内容，例如动作、重量、组数和次数。助理需要结合近期训练、睡眠、饮食和身体状态：

- 总结训练变化；
- 识别可能的平台期或恢复不足；
- 对动作质量、训练安排和突破方式给出一般性建议；
- 不将缺少完整记录时的推测表述为确定结论。

### 12.6 症状与近期状态关联

用户报告头疼、腹泻、食欲下降等症状时，助理可以检索本人近期睡眠、饮食、运动、体温和其他症状记录，提出可能相关因素、观察事项和适合就医的条件。

### 12.7 跨成员健康事件关联

当用户报告某项可能影响家庭的症状时，助理可以检索家庭成员近期相关事件和共同经历。例如多名成员同期腹泻时，可以提示共同食物暴露或感染的可能性，并给出观察与就医建议。

此类回答必须说明依据和不确定性，不作确定诊断。

### 12.8 儿童连续记录

家庭成员可以代儿童记录身高、体重、饮食、食欲、排便、体温和其他状态。助理需要支持：

- 按时间查看身高体重变化；
- 结合近期饮食和活动提供一般性建议；
- 在拥有可靠年龄、性别和参考数据时进行生长趋势比较；
- 缺少权威参考数据时不声称给出精确生长百分位；
- 对需要专业评估的异常变化建议咨询儿科医生。

### 12.9 餐前健康决策

用户可以在进食前拍照或描述计划食用的餐食。系统需要区分“计划食用”和“实际摄入”：

- 餐前结合个人健康资料和营养数据给出份量及搭配建议；
- 餐后允许用户补充实际吃了多少；
- 只有实际摄入记录进入已完成饮食历史；
- 缺少连续血糖等个人数据时，不给出确定的餐后血糖数值预测。

### 12.10 医嘱录音理解

用户可以上传就诊时的医嘱录音。系统需要：

- 保存原始录音和转写文本；
- 识别药物、用法、检查、复诊时间和注意事项；
- 对关键药名、剂量、频率和时间要求用户确认；
- 使用通俗语言辅助解释；
- 将用户明确确认的复诊或执行事项转成提醒候选；
- 不替代医生原始医嘱，存在歧义时建议向医生或医疗机构确认。

## 13. 外部实时与专业数据

### 13.1 按需调用原则

v1 可以接入用户提供的营养、天气和地点 API。用户提出相关问题时，Agent 可以自行选择合适工具，取得实时或专业数据后与家庭健康记录综合分析。

外部 API 提供事实数据，大模型负责理解问题和形成建议。API 不可用时，助理应明确说明数据缺失，并降级为一般性建议，不得伪造实时信息。

### 13.2 营养数据

系统应支持搜索食物、获取标准营养数据并按估算摄入量换算。图片识别结果、用户描述和营养 API 数据共同形成营养估算。

估算结果应保存食物匹配项、份量、营养数值或范围、数据来源和估算时间，以支持未来一致的历史分析。

### 13.3 天气数据

系统应支持按需获取当前天气、预报和天气预警，并结合成员近期状态回答保暖、运动和出行相关问题。

v1 不自动每天推送天气简报；该能力放入后续路线图。

### 13.4 地点与出行数据

系统应支持按需搜索地点、读取地点详情和基础出行条件，并结合家庭成员近期状态辅助判断某项家庭活动是否合适。数据不足时应明确说明，不能自行编造地点属性。

## 14. 家庭成员查询与公共知识

### 14.1 查询原则

- 用户无需切换身份即可询问其他成员；
- 查询本身不产生新的健康事实；
- 回答只使用有效、未撤回的记录；
- 回答应围绕当前问题检索相关信息，不应每轮把全家全部资料发送给模型；
- 普通成员能够查询其他成员，不代表个人事件自动变成共同事件；数据访问权限、事件相关成员、内容适用成员和家庭公共知识不得混淆；
- 查询结果必须明确所描述的成员，避免串人。

### 14.2 公共知识写入

v1 仅在用户明确表达家庭共享意图时写入，例如：

- “全家记住，我们最近都低盐饮食”；
- “记录到家庭：妈妈这周得了流感”；
- “这件事以后大家问的时候都可以告诉他们”。

自动判断并写入家庭公共知识的能力属于未来扩展，v1 默认禁用。

## 15. 提醒

### 15.1 创建

提醒必须由用户主动提出，例如：

- “每天晚上八点提醒我吃药”；
- “下周三提醒我复查”；
- “两个月后提醒我预约体检”；
- “每周日提醒我量血压”。

Agent 识别后必须复述内容和时间，并在用户确认后创建。

### 15.2 支持能力

- 单次提醒；
- 重复提醒；
- 查看已有提醒；
- 标记完成；
- 稍后提醒；
- 修改时间或内容；
- 暂停和恢复；
- 取消。

### 15.3 送达

- 主要通过 Android PWA 系统通知弹出；
- 应用内保留待完成、已完成、延后和取消状态；
- PWA 聊天首屏明显展示今日待办和逾期提醒；
- 用户当天首次打开应用或发起对话时，Agent 可以顺带提示由该用户主动创建且已经到期或即将到期的提醒；
- 点击系统通知进入对应提醒或对话；
- v1 只通知提醒设置者；
- 不因未确认或逾期自动通知其他家人；
- 推送可能受系统权限和后台限制影响，不宣称具备医疗级报警可靠性。

家庭默认时区为 Asia/Shanghai。以后处理跨时区时再询问提醒是否跟随当地时间。

## 16. 客户端需求

### 16.1 形态

- v1 使用移动优先的 PWA；
- 可添加到 Android 主屏幕；
- 后端保持渠道无关，以后可以接入 IM 或其他客户端；
- v1 不开发原生 App。

### 16.2 核心界面

成员端以聊天为首屏，至少包含：

- 对话消息流；
- 文字输入；
- 录制语音；
- 拍照、选择图片和上传 PDF；
- AI 回复播放按钮；
- 记忆提示、修改和撤回；
- 今日提醒或待办入口；
- 当前身份、通知权限、应用版本和退出当前设备等最小信息。

v1 不建设管理员 Web 界面。管理员通过配置、Secrets、管理 CLI、结构化日志和只读查询完成成员、设备、数据、失败任务、调用量与备份运维。

### 16.3 老人可用性

- 首屏直接进入聊天；
- 字号和触摸区域足够大；
- 主要操作可通过语音完成；
- 不要求理解数据库、档案或结构化数据等概念；
- 错误提示使用普通语言；
- 避免在单一页面堆积大量按钮和设置。

## 17. 数据保存、修改与恢复

### 17.1 保存规则

- 对话永久保存；
- 用户消息和 AI 回复永久保存；
- 语音原文件和转写文本永久保存；
- 图片和 PDF 永久保存；
- 成员档案永久保留；
- 不提供常规的“删除家庭成员”产品流程；
- 记忆允许撤回，但保留其来源和撤回历史；
- 管理员修改内容时保留修改前数据和操作时间。

### 17.2 文件要求

- 文件必须绑定家庭、成员、消息和上传者；
- 保存文件类型、大小、哈希、原始名称和上传时间；
- 同一文件重复上传或任务重试时，应避免形成失控的重复副本；
- 文件上传失败不得显示为成功。

### 17.3 备份

v1 必须具备数据库和附件自动备份能力：

- 备份不能只保存在同一块服务器磁盘；
- 备份需要加密；
- 保留多个历史版本；
- 必须能够从备份恢复；
- 上线验收包含至少一次恢复演练。

备份必须离开当前服务器，并至少支持一种由管理员提供的外部目标，例如 S3 兼容对象存储、NAS、WebDAV 或其他可验证的远程存储。备份凭据不得进入代码库或普通日志。

## 18. 异常与降级体验

- 用户输入先保存，再调用外部 API；
- 外部 API 失败时提示“暂时无法处理，内容已经保存，请稍后重试”；
- 原始消息和附件不得因模型、ASR、TTS 或 PDF API 失败而丢失；
- 失败任务支持稍后重试；
- 重试不得重复创建同一记忆或提醒；
- 新消息使旧回复失效时，已经保存的消息、附件、处理状态、调用记录和动作记录不得丢失；
- 已完成且仍有效的基础处理结果应尽量复用，已经提交的业务变更不得重复执行；
- ASR 失败时允许用户改用文字；
- TTS 失败时文字回复仍可阅读；
- 推送失败时提醒仍保留在应用内；
- 记忆提取失败不阻止继续聊天；
- 用户需要看到“上传中、转写中、正在阅读报告、处理中、处理失败”等明确状态；
- 普通用户错误提示保持简洁，详细错误通过管理员日志和 CLI 查询。

## 19. 隐私与安全要求

- 健康档案、对话索引、提醒和附件保存在自有服务器；
- 模型推理、语音和文档处理可以使用云 API；
- 选择明确承诺不使用 API 用户数据训练模型的供应商；
- 调用 API 时只发送完成当前任务所需的信息；
- 客户端不保存完整健康档案，仅保留必要的登录和界面状态；
- 全站使用 HTTPS；
- 邀请链接一次性使用且具有有效期；
- 公开网页读取必须阻止本机、内网和受保护基础设施访问；
- API 密钥不得发送到客户端或出现在普通日志中；
- 管理员操作需要审计；
- 系统必须防止外部人员通过未授权访问获取家庭数据。

管理员能够查看所有家庭数据属于产品既定权限，不视为越权行为。

## 20. AI可审计性

系统应尽量保存并展示回答依据：

- 使用了哪些成员的资料；
- 引用了哪些记忆、体检报告或饮食记录；
- 数据截止时间；
- 哪些内容是本人陈述、家人代记录或报告提取；
- 哪些内容尚未确认；
- 哪条原始消息或附件形成了记忆；
- 使用的模型及调用时间；
- 模型提出并执行了哪些系统动作；
- 哪次处理被新消息取代、哪些结果得到复用，以及哪些业务动作最终实际生效。

面向普通成员的回答不需要暴露技术日志，但应提供清晰、可理解的事实依据。

## 21. 技术与扩展约束

以下属于已经确定、会影响需求实现的技术约束，但本文不展开详细设计：

- 以 TypeScript 为主语言；
- 自主实现 Agent Core、会话流程和插件体系；
- 可以参考 DeepSeek Harness、Hermes、OpenClaw 等项目，但不以其作为运行时底座；
- 采用模块化单体，而非 v1 微服务；
- LLM、ASR、TTS、图片和 PDF 理解均通过可替换云 API；
- 不运行本地模型；
- v1 对 TTFT 不敏感；
- 外部能力通过明确 Provider 接口接入；
- v1 插件随代码发布，不支持在线安装任意第三方插件；
- 健康业务数据不应存放在某个模型供应商或 Agent 框架的专有记忆中；
- 管理员使用版本化配置文件、环境变量或 Secrets、管理 CLI 和结构化日志运维；
- 管理 CLI 的修改操作必须经过业务校验并保留审计记录；
- v1 默认输入上下文预算暂定为 256k tokens，并允许通过配置调整；实际预算不得超过当前模型能力，并应为输出和工具结果预留空间；
- 原始资料永久保存，但每轮仅选择当前问题需要的内容；超过上下文预算时应分批处理、摘要或向用户说明，不得静默遗漏关键依据。

预期插件类型包括：

- ModelProvider；
- SpeechToTextProvider；
- TextToSpeechProvider；
- DocumentProvider / AttachmentProcessor；
- AgentTool；
- NotificationProvider；
- ChannelAdapter；
- NutritionProvider；
- WeatherProvider；
- PlaceProvider。

## 22. LLM Provider 与未来多模型扩展

v1 仅实现单模型处理，不实现多模型讨论、审查、投票或裁判。系统应保持健康业务与模型调用分离，允许替换 LLM Provider，并记录每次调用所用模型、耗时、Token、费用和错误。

复杂问题的多 LLM 协作属于后续路线。v1 不要求为其建设编排系统；如果提前预留会显著增加复杂度，允许以后通过受控重构实现。未来参与协作的模型仍不得绕过正常业务校验直接修改健康数据或创建提醒。

## 23. v1 功能清单

### 23.1 必须实现

- 单家庭；
- 管理员创建成员；
- 可登录成员与受管理成员；
- 一次性邀请链接或二维码、设备长期登录、设备撤销和重新邀请；
- 独立聊天；
- 处理期间继续发送消息、旧回复失效和后续重新综合；
- 操作者与事件主体分离；
- 文字、方言语音、图片和 PDF 输入；
- 文字回复及点击播放语音；
- 对话和附件永久保存；
- 基础档案逐步完善；

## 24. 后期扩展路线

### 24.1 智能健康设备

接入手环、体脂秤、血压计、血糖设备及其他传感器，自动形成带设备来源和测量时间的健康事件。

### 24.2 智能家居

接入空调、温湿度、空气质量、冰箱食材等家庭设备。Agent 可以在受控权限下读取状态，并在用户明确授权后执行调整。

### 24.3 主动环境简报

按计划主动获取天气、空气质量和家庭日程，为不同成员生成个性化建议，例如降温时提醒关节不适成员注意保暖。

### 24.4 多 LLM 协作

对于复杂问题，可使用生成加审查、并行专家或多方案加裁判等编排策略。该能力遵循第 22 节的扩展要求。

### 24.5 家庭安全监测

接入摄像头或其他传感器提供的受控事件，支持碰撞、跌倒等异常检测，并根据预先设置的规则联系家庭成员或紧急服务。该能力涉及误报、设备可靠性和自动外呼规则，需要独立需求设计。

### 24.6 多源家庭决策辅助

持续增加健康设备、家庭环境、实时天气、地点、日程和其他可信信息源，使 Agent 能够在说明依据和不确定性的前提下进行更多维度的家庭决策辅助。

## 25. 验收场景

v1 发布前至少完整通过以下场景：

1. 管理员通过 CLI 创建自己、另一名可登录成员和一个无手机儿童；
2. 多台 Android 设备通过各自一次性邀请链接或二维码进入正确账号；管理员能够通过 CLI 撤销旧设备并重新邀请；
3. 家庭成员可以发送文字、方言语音、饮食照片和体检 PDF，并收到回复；
4. 用户拍饭菜并说“米饭只吃了一半”，系统记录实际摄入而非整份；
5. 用户修改或撤回刚生成的记忆，后续回答不再引用旧内容；
6. 爸爸替儿童记录体温，系统正确保存事件主体与记录人；
7. 用户问“最近妈妈健康怎么样”，回答引用正确成员的数据并说明截止时间；
8. 用户上传两份不同日期的体检报告，系统能够比较相同指标；
9. 系统根据成员历史、检查时间和异常记录推荐本次体检项目并说明原因；
10. 用户创建吃药提醒，Android 到期弹出通知，支持完成、延后、修改和取消；
11. 用户明确要求写入家庭公共知识后，其他成员查询时可以使用；
12. 模型、ASR、TTS 或 PDF API 临时失败时，消息和附件不丢失；
13. 重试同一失败任务不会重复写入记忆或提醒；
14. 管理员能够通过 CLI 或只读查询追溯一条记忆来自哪条消息或附件，并查看相关审计和模型调用量；
15. 完成一次数据库与附件备份恢复演练；
16. 全流程没有发生操作者、事件主体或被查询成员串人；
17. 用户同时报告睡眠、体重和早餐，系统能分别记录并给出综合建议；
18. 用户记录训练动作、重量、组数和次数，后续询问时能结合历史训练分析；
19. 用户报告头疼时，系统能检索近期睡眠等相关记录并说明可能关联；
20. 多名成员近期出现相似症状时，系统能检索共同饮食或家庭事件并给出观察建议；
21. 家长代儿童记录身高、体重、饮食、食欲或排便，后续可以按时间查询；
22. 用户餐前拍照获得建议，餐后补充实际摄入，系统不把计划食用量当成实际摄入；
23. 用户提供体检项目清单或链接，系统能结合个人历史进行筛选；
24. 用户上传医嘱录音，系统保存原音、转写并要求确认关键药名和剂量；
25. 用户询问天气或家庭出行问题时，系统能按需调用天气和地点 API；
26. 饮食分析能按需调用营养 API，并保存营养数据来源；
27. 用户发送公开网页链接时，系统能读取可访问正文；遇到登录页、复杂页面或失败时，能够提示用户改发文字、截图或 PDF；
28. 长录音或大型 PDF 处理时，用户能看到阶段状态；外部处理失败后，已上传原件仍然存在；
29. Web Push 不可用时，用户仍能在 PWA 首屏或当天对话中看到已创建的到期提醒；
30. 单轮上下文预算可由管理员配置为 256k 或其他值，超限处理不会静默遗漏关键健康依据；
31. 管理员无需 Web 后台即可通过配置、Secrets、CLI 和日志完成 v1 运维操作；
32. 用户在回复生成前补充“刚才说的是乐乐，不是我”，旧回复停止并按正确成员重新处理，两条原始消息和被取代记录均被保留；
33. 用户连续补充同一健康事件时，系统重新综合新旧消息，复用仍然有效的附件解析结果，不继续执行过时动作；
34. 旧处理已经成功写入事件后又被新消息取代，系统不会重复写入；如果新消息明确纠正该事件，则保留修改、撤回或更正关系；
35. 旧回复只提出尚待确认的提醒候选，新消息使其失效后，系统不会自动创建提醒；
36. 用户报告多名成员共同出现相似症状时，系统建立关联相关成员的共同事件，并能保存每名成员不同的开始时间和严重程度。

## 26. 试用成功标准

技术验收通过后进行至少两周家庭试用。v1 被认为具备继续迭代价值，需要满足：

- 所有计划使用的家庭成员能够独立进入并完成对话；
- 老人使用语音时不需要管理员频繁协助；
- 没有发生身份串人、严重错误归档或附件归属错误；
- 饮食记录、查询家人近况、体检建议三个核心场景均被自然使用；
- 用户能够理解“已记住”提示，并能成功修改或撤回；
- 查询家人健康状况的回答被认为真实且有用；
- 用户创建的提醒能够在家庭 Android 设备上正常弹出；
- API 费用和服务器资源消耗在家庭可接受范围内；
- 用户愿意在两周后继续使用，而不是仅完成测试任务；
- 普通成员除首次邀请和系统权限授权外，无需进入配置或管理页面；
- 家庭成员可以自然记录睡眠、身体测量、训练和症状，无需进入专门模块；
- Agent 能够在至少一个真实场景中正确调取不同类型或不同成员的相关历史；
- 营养、天气或地点 API 的结果能够参与回答，且服务不可用时不会伪造数据。

- 图片和 PDF 处理供应商及文件大小限制；

- 默认 256k 上下文预算在所选模型上的可用性、费用和输出预留。

## 28. 需求变更原则

- 优先从真实家庭使用中发现需求，不提前建设完整健康平台；
- 新功能应首先判断是否能通过聊天自然完成；
- 高频且需要准确查询的数据再升级为专门结构化模块；
- 新能力不得破坏操作者与事件主体的区分；
- 新模型、渠道和供应商应通过可替换接口接入；
- 原始资料、来源关系和修改历史必须持续可追溯；
- 为未来扩展预留接口，但如果预留会显著增加 v1 复杂度，允许以后通过受控重构实现。
